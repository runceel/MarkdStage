# AI を使ったスライド作成

> English version: [English](../ai-assisted-authoring.md)

外部の AI ツールで Markdown の下書きや修正を行い、MarkdStage で確認します。
連携には次の 2 つの方法があります。

| 環境 | 準備と参照できる情報 |
| --- | --- |
| Windows Desktop と同梱 CLI | ワークスペース画面の **Install skills…** で導入し、Codex、Claude Code、GitHub Copilot でも同じフォルダーを開きます。エージェントは Markdown と CLI 診断を使い、Desktop はローカルの確認・編集画面になります。 |
| Canvas Extension を導入した GitHub Copilot App | Extension を導入すると、Copilot は Canvas のガイド・検証ツールと、表示中の Canvas デッキのコンテキストを利用できます。 |

Desktop は AI チャットを内蔵せず、選択中のスライドやワークスペースを外部エージェントへ自動共有しません。
AI にはソースのファイル名を伝え、同じフォルダーを使います。スキル導入は AI ツール本体や
Canvas Extension のインストールではありません。
依頼例と実際のアプリ画面は [Windows 操作チュートリアル](windows-walkthrough.md)を参照してください。

![Markdown デッキを開いた MarkdStage Canvas Extension](../images/canvas-main.png)

## Copilot が参照できる情報

Copilot がスクリーンショットだけからプレゼンテーション形式を推測せずに済むよう、
MarkdStage は用途を絞った情報を渡します。

| 情報 | 執筆でどう役立つか |
| --- | --- |
| スライド形式のガイダンス | スライド区切り、フロントマター、レイアウト、コンテンツサイズ、スピーカーノート、使える Markdown を説明する |
| テーマのガイダンス | 組み込みテーマと選び方を説明する |
| カスタムテーマのガイダンスとスキーマ | 使える CSS カスタムプロパティ、メタデータ、アセット、セキュリティ上の制約を定義する |
| Architecture DSL のガイダンスとスキーマ | 要素、レイアウト、アイコン、コネクター、上限、検証規則を定義する |
| 現在のデッキ内容 | 表示中の Markdown を、そのまま修正対象として渡す |
| Architecture の検証 | 該当スライド、図ブロック、JSON パス、直し方を含む構造化エラーを返す |
| 固定 16:9 レイアウト診断 | 見切れるページを特定し、はみ出し量と関係する要素を報告する |
| 必要なスライドの画像 | 目で確かめたいページや問題のあるページを 1280x720 の画像にする |

Canvas を開いている間、表示中のデッキと Architecture DSL は GitHub Copilot App のコンテキストに
含まれます。さらに詳しい情報が必要になれば、Copilot は上記のリファレンスや診断を自分で取得できます。

以下のツール名は Canvas 連携を対象としています。Desktop と CLI では、
`markdstage guide`、`validate`、`inspect`、`capture` が対応するコマンドです。

`markdstage_guide` ツールは、`slide-format`、`themes`、`custom-themes`、`theme-schema`、
`architecture-dsl`、`architecture-schema` といったトピック単位で執筆用の情報を返します。
Architecture DSL を書く前に、まず `architecture-schema` を取得します。Schema から生成した
全要素のフィールド、条件付き必須項目、自己完結した例を 8 KiB UTF-8 以内で返します。
独立した `markdstage_validate` ツールでは未表示の内容を検証でき、Canvas のアクションでは
表示済みの内容の検証、固定レイアウトの診断、選んだスライドの画像化を行えます。

こうした仕組みにより、Copilot はまず Markdown の文法と数値で測れる情報をもとに判断し、
目で見ないと分からない問題だけを画像で確かめられます。

目的と条件を具体的に伝えれば、作成、表示、確認のほとんどをチャットだけで進められます。
変更内容は常に Markdown ソースと Canvas の表示で確かめられます。

実際のやり取りをたどりたい場合は、
[ハンズオン: GitHub Copilot でデッキを作成する](copilot-hands-on.md)を参照してください。

## おすすめの進め方

1. **元になる資料と発表の目的を伝えます。** 元になるファイルやメモ、聞き手、発表の狙い、使いたいテーマ、
   おおよその分量を示します。
2. **Markdown デッキをひととおり作らせます。** Copilot は作成用契約を参照し、
   すべてのスライド断片を書きます。
3. **表示前に検証します。** `markdstage_validate` で、独立した Architecture DSL の問題を
   まとめて修正します。不完全な検証結果を成功扱いしません。
4. **同じ内容を保存・表示して確認します。** 検証済みの DSL を再生成せずに Canvas へ渡し、
   流れ、情報量、図、スピーカーノート、用語を確認します。
5. **固定 16:9 の出力を調べます。** レイアウト診断が、PDF と同じ条件で見切れるページを特定し、
   直すための数値を返します。
6. **目で確かめたいページだけを画像にします。** デッキ全体を画像化しなくても、必要なページの
   PNG だけで、バランス、余白、図の見え方を Copilot が判断できます。
7. **直して確認を繰り返します。** Copilot が Markdown を更新してデッキを読み込み直し、
   発表や書き出しに耐える状態になるまで、直したページを調べ直します。

```text
元になる資料と発表の目的
  → MarkdStage のガイダンスとスキーマ
  → Markdown デッキ
  → 読み取り専用の Architecture 事前検証
  → Canvas での表示
  → 固定 16:9 診断
  → 必要なスライドだけを画像化
  → Markdown を修正
  → プレゼンテーションまたは PDF
```

## 伝わる依頼を書く

デッキの構成と見た目を左右する情報を盛り込みます。

- 元になる資料または Markdown のパス
- 聞き手と発表の狙い
- 想定時間またはスライド枚数
- 使いたいテーマやブランド上の制約
- 必要なセクション、図、ノート、用語
- 固定 16:9 の PDF 出力まで確認するかどうか

### 資料からデッキを作成する

```text
proposal.md から8枚のアーキテクチャレビュー資料を作成してください。
Microsoft テーマを使用し、スピーカーノートを追加して、システム概要には Architecture DSL を使用してください。
デッキ全体を MarkdStage で開き、エクスポート前に 16:9 のクリッピングを修正してください。
```

### 既存のデッキを修正する

```text
技術者向けの資料として slides.md をレビューしてください。
セクションの順序とすべてのコード例を維持したまま、情報量の多いスライドを整理してください。
修正後にデッキ全体を開き直し、固定 16:9 レイアウトを確認してください。
```

### 特定の図を改善する

```text
サービス境界とデータフローを追いやすくするため、4枚目の Architecture DSL を更新してください。
図を検証してスライドを表示し、ラベルやコネクターが重なる場合は配置を修正してください。
```

### 出力上の問題を調べる

```text
このデッキを PDF 相当のクリッピングについて検査してください。
対象の Markdown ページを修正し、視覚的な確認が引き続き必要なページだけを画像化してください。
```

## 検証機能を理解する

### 表示前の検証（`markdstage_validate`）

DSL 本文には `{ "format": "dsl", "source": "..." }`、一枚ずつのスライド断片には
`{ "format": "slides", "slides": ["..."] }` を使います。Canvas インスタンスは不要で、
ファイル、表示内容、現在ページ、編集・保存状態を変更しません。
API 実行の `ok` と、内容の `valid`、検証の `complete`、打ち切りの `truncated` は別です。

診断には安定したコード、JSON Pointer、重大度、文脈に応じた修正候補を含みます。
スライド入力にはページとブロック位置も付与します。独立した問題はまとめて返しますが、
不正 JSON や構造の前提不足では依存する検証を止め、件数・処理量の上限到達を明示します。
修正候補を自動適用して既存値を上書き・統合・削除することはありません。
v1 の受け入れ動作は維持し、親レイアウトで無視される座標などは作成上の警告として区別します。

DSL の検証だけでは、画像ファイルの実在、ページへの収まり、視認性までは保証しません。

### 表示済み Architecture の検証（`get_architecture_errors`）

Architecture の検証は、デッキ全体または選んだスライドについて、機械可読なエラーを返します。
Copilot は該当ページ、Architecture ブロック、JSON パス、直し方をもとに、
試行錯誤だけに頼らずにソースを直せます。事前検証と同じ規則を利用し、既存のブロック単位の
エラー一覧を維持したまま、詳細な診断と段階ごとの完全性情報も返します。

### 固定 16:9 の検査（`inspect_layout`）

固定レイアウトの検査は、PDF と同じ 1280x720 の領域で描画し、はみ出したページを報告します。
診断結果には、縦横それぞれのはみ出し量と、問題箇所の近くにある要素の一覧が含まれます。

![縦方向のクリッピング警告を表示した固定 16:9 プレビュー](../images/canvas-layout-warning.png)

この診断で分かるのは、内容がページに収まるかどうかだけです。
説明の分かりやすさ、情報の優先順位、見た目のバランスは、人の目で確かめる必要があります。

### 必要なスライドの画像化（`capture_slides`）

スライドの画像化では、指定したページだけを PNG ファイルとして書き出します。
ページを指定しない場合は、MarkdStage が先にデッキを検査し、クリッピングのあるページだけを
画像にできます。書き出したファイルはワークスペースに残り、同じセッション内で Copilot が確認できます。

画像化は、構造化された診断の後に使う手段です。全ページを見るための既定の方法ではありません。

## 作成者の責任

AI が生成した内容も含め、最終的なデッキの内容に責任を負うのは作成者です。

- Markdown ソース内の事実、名称、コード、機密情報を確かめてください。
- スピーカーノートに、発表者向けとしてふさわしい内容だけが入っているか確かめてください。
- 図はスキーマの妥当性だけでなく、技術的に正しいかどうかも確かめてください。
- 配布前に、書き出した PDF を全ページ目視してください。
- プロジェクトの一部として使うデッキは、ソースファイルをバージョン管理してください。

使用する AI サービスへ送信することを組織のポリシーが認めた資料だけを使用してください。
デモでは架空の名称、サンプルデータ、独立したワークスペースを使います。
MarkdStage がローカルで動くことと、外部 AI サービスのデータ取り扱いは別です。
